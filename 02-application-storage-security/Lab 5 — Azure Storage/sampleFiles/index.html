Azure Storage,
built hands-on.

A practical learning note on where Azure stores data, how Blob Storage works, and the security choices that matter when applications depend on it.

Applications are only as dependable as the data beneath them.

Azure Storage provides durable cloud data services for application files, shared file systems, queues, and structured key-value data. In this lab, I created a StorageV2 account, made a blob container, and uploaded sample application files through the Azure portal.

01 / Choose the right service

Four storage types. Different jobs.

Start with the data shape and access pattern. The storage service follows from what the application needs to do.

01

Blob Storage

Object storage for unstructured data: documents, images, backups, logs, and media.

02

Azure Files

Managed file shares that applications and users can access over familiar file protocols.

03

Queue Storage

Simple message queues that help decouple application components and background work.

04

Table Storage

A NoSQL key/attribute store for large amounts of structured, non-relational data.

02 / The lab

From account to uploaded object.

A small portal-based workflow made the storage hierarchy tangible: account, container, then blobs.

  1. Create a StorageV2 account

    Choose a subscription, resource group, region, performance tier, and redundancy option. This lab used Standard performance and locally redundant storage (LRS).

  2. Create a private blob container

    Containers organize blobs within an account. Keep anonymous access disabled unless public access is an explicit, reviewed requirement.

  3. Upload application files

    Upload sample files and confirm their names, type, size, and access tier in the portal. This lab includes application.log and sample.txt.

  4. Verify the configuration

    Review account properties and container settings. Consider access, redundancy, lifecycle, and recovery before storing real application data.

03 / Security fundamentals

Storage security is a set of decisions.

A storage account is a boundary, not a complete security strategy. Apply least privilege at each access path.

01

Prefer identity-based access

Use Microsoft Entra ID and Azure RBAC where supported. Grant only the required data actions and scope access as narrowly as practical.

02

Protect keys and SAS tokens

Account keys provide broad access. Avoid embedding them in applications; rotate when exposed. Use narrowly scoped, short-lived SAS only when needed.

03

Restrict network exposure

Disable public blob access unless required. Use firewall rules, private endpoints, and trusted network paths according to the application design.

04

Require encrypted transport

Require secure transfer and use HTTPS for client connections. Azure Storage encrypts data at rest by default; understand your key-management requirements.

05

Plan for recovery

Choose redundancy based on availability and recovery objectives. Evaluate soft delete, versioning, and backups for accidental deletion or change.

06

Monitor and minimize data

Enable relevant diagnostic logs and alerts. Apply lifecycle policies, retention requirements, and data classification to control risk and cost.

Lab vs. production: This lab used access-key authentication to learn the portal workflow. For production workloads, evaluate Microsoft Entra ID and scoped Azure RBAC before relying on shared account keys.
